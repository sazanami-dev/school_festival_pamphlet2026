# スタンプラリー 設計書

学園祭2026 デジタルパンフレットに組み込むデジタルスタンプラリーの設計。
企画概要（目的・基本の流れ）は企画書を参照。ここでは「どう作るか」を決める。

- 対象リポジトリ：本リポジトリ（Next.js 16 App Router / PostgreSQL / Drizzle ORM）
- 状態：実装済み（チェックポイント・景品名・開催日などは仮の値。8章の未定事項を参照）

---

## 1. 方針（決定事項）

| 項目 | 決定 | 理由 |
|---|---|---|
| 参加者の識別 | 参加ボタンを押すとサーバーがランダムなIDを発行し、Cookie に保存する | 個人情報を一切集めない。配布物・受付が要らない |
| 登録情報 | なし（ニックネームも持たない） | 目的に不要なため |
| 引き継ぎ | 文字の「引き継ぎコード」を入力して復元する | 同じ端末では自分の画面のQRを読めないため |
| チェックポイントQR | 固定のQRを印刷して掲示する | 運用が楽。スタッフの常駐が要らない |
| 不正対策 | QRの写真共有・IDの作り直しによる多重取得は**許容**する | 景品が高価ではないため。手間に見合わない |
| 二重交換 | 同じIDでの景品交換は1回だけ（サーバーで記録） | これは簡単に防げるので防ぐ |
| 景品 | 1種類。スタンプ **8個** で交換、**1人1回** | 企画側の決定 |
| 交換所 | サークルの展示場所 | 企画側の決定 |
| 受付時間 | 開催日の **10:00〜16:00**（スタンプ取得・交換とも） | 企画側の決定 |

## 2. 利用者の種類

| 種類 | できること | 必要なもの |
|---|---|---|
| 通常利用者 | パンフの閲覧のみ | なし（IDは発行しない） |
| 参加者 | スタンプ取得・一覧・景品交換 | 参加ボタンで発行されるID（Cookie） |
| 交換所スタッフ | 交換の確認・確定 | スタッフ用PIN |
| 運営（開発者） | チェックポイント・景品の設定、QRの印刷、集計の確認 | リポジトリとDBへのアクセス |

## 3. 画面とURL

ボトムナビの「スタンプ」（`/stamp`、[BottomNav.tsx](../src/components/BottomNav.tsx)）が入口。

| URL | 画面 | 内容 |
|---|---|---|
| `/stamp` | スタンプ トップ | **未参加**：遊び方の説明、「参加する」ボタン、「引き継ぎコードを入力」リンク<br>**参加済み**：獲得数（例 3/8）、スタンプ一覧（獲得・未獲得）、「QRを読む」ボタン、景品交換への導線、引き継ぎコードの表示 |
| `/stamp/scan` | QRスキャナ | カメラでチェックポイントQRを読む。カメラが使えないとき用に「コードを手入力」欄 |
| `/s/[token]` | （画面なし） | チェックポイントQRのリンク先。**Route Handler（GET）** で、処理したらリダイレクトする（4.3） |
| `/stamp/join?cp=<token>` | 参加の選択 | Cookie のない人が `/s/[token]` から来たときの画面。「はじめて参加する」「引き継ぎコードを入力する」を選び、そのままスタンプも付ける |
| `/stamp/recover` | 引き継ぎ | 引き継ぎコードを入力して復元 |
| `/stamp/exchange` | 景品交換 | 交換条件（8個）と交換所の場所。条件を満たしていれば交換用QRを表示 |
| `/staff` | スタッフ ログイン | PINを入力 |
| `/staff/exchange` | 交換の確認 | 参加者の交換用QRを読み、内容を確認して「交換済みにする」 |

- スタンプ系の画面は参加者ごとに内容が変わるので、リクエスト時に描画する（Cache Components では `connection()` 以降でDBを読む。README の「DBアクセスの注意」参照）。
- `/staff` 配下はボトムナビを出さない（`HIDDEN_PATHS` に追加）。
- **Cookie の設定とDBの更新は、Server Action か Route Handler の中だけで行う**。Next.js 16 では、ページの描画中に Cookie を設定できず、描画中のDB更新も禁止されている（同梱ドキュメント `data-security.md`「Avoiding side-effects during rendering」、`cookies.md`）。ページ（Server Component）は読むだけにする。

## 4. 主な流れ

### 4.1 参加する
1. `/stamp` で「参加する」を押す
2. サーバーが参加者ID（UUID v4）と引き継ぎコードを発行し、DBに保存
3. 参加者IDを Cookie に保存して `/stamp` を再表示
4. 引き継ぎコードを大きく表示し「スクショかメモをしてください」と案内する

### 4.2 スタンプを取る（パンフ内スキャナ：基本の方法）
1. `/stamp` の「QRを読む」→ `/stamp/scan`
2. QRを読むと、中のURLからトークンを取り出してサーバーに送る
3. サーバーが（参加者ID, チェックポイント）を保存。すでにあれば何もしない
4. 「〇〇のスタンプを獲得！」または「獲得済みです」を表示

パンフ内で読む理由：iPhone の標準カメラで読むと Safari が開くため、LINE / Instagram のアプリ内ブラウザや「ホーム画面に追加」から開いている人は、Cookie が別になりスタンプが分かれてしまう。

### 4.3 スタンプを取る（標準カメラで読まれた場合）
`/s/[token]` は画面を持たない **Route Handler（GET）** にする。ページを開いた（描画した）ときにスタンプを付ける形にはしない（3章の注意）。

QR のリンク先 `/s/[token]` を開いたとき：
- **トークンが無効** → `/stamp?error=invalid` へリダイレクトし、「無効なQRです」を表示
- **受付時間外** → `/stamp?error=closed` へリダイレクト
- **Cookie あり（有効な参加者ID）** → Route Handler の中でスタンプを保存し、`/stamp?got=<checkpointId>` へリダイレクト。`/stamp` は `got` を見て「〇〇のスタンプを獲得！」または「獲得済みです」を表示する
- **Cookie なし** → `/stamp/join?cp=<token>` へリダイレクト。**このときIDは作らない**
  - 何も聞かずに新しいIDを作ると、別のブラウザで集めていた人のスタンプが分かれてしまうため
  - `/stamp/join` で「はじめて参加する」を押すと、Server Action が「参加（4.1）＋そのチェックポイントのスタンプ付与」をまとめて行う
  - 「引き継ぎコードを入力する」を選んだ場合も、Server Action が「引き継ぎ（4.4）＋スタンプ付与」をまとめて行う
  - どちらも終わったら `/stamp?got=<checkpointId>` へリダイレクト

GET でDBを更新することについて：
- Next.js は通常、更新を POST（Server Action）で行うよう勧めている。ここではQRから直接開くためGETにしている。
- 影響を確認した結果、問題はない：
  - LINE などのリンクプレビュー（URLを先読みする機能）には Cookie がないので、`/stamp/join` へのリダイレクトになるだけで何も保存されない。
  - 他のサイトから `/s/...` を踏ませても、本人にスタンプが付くだけ（不正は許容）。
  - 同じスタンプを何度付けても1つにしかならない（6章の主キー）。

### 4.4 引き継ぐ
1. `/stamp/recover` で引き継ぎコードを入力
2. 一致する参加者がいれば、その参加者IDを Cookie に付け直す
3. このブラウザに別のIDがあった場合は上書きする（統合はしない。確認ダイアログを出す）

### 4.5 景品を交換する
1. 8個集まると、`/stamp` に「景品と交換できます」と交換所（サークルの展示場所）の案内が出る
2. 交換所で `/stamp/exchange` を開き、「交換する」を押すと交換用QRを表示（有効期限つきの署名トークン。5.4 参照）
3. スタッフが `/staff/exchange` でQRを読む → 獲得数と交換済みかどうかが出る
4. スタッフが景品を渡して「交換済みにする」を押す
5. 参加者の画面は「交換済み」に変わる（画面を開き直す or 数秒おきに確認）

## 5. 仕様の詳細

### 5.1 参加者ID と Cookie
| 項目 | 値 |
|---|---|
| ID | UUID v4（推測できない乱数。連番は使わない） |
| Cookie 名 | `sr_pid` |
| 属性 | `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=30日` |

- `SameSite=Lax` なので、標準カメラからリンクを開いた場合でも Cookie は送られる。
- ID はDBの主キーとしてそのまま使う。Cookie の中身を書き換えられても、存在しないIDなら「未参加」として扱う。

### 5.2 引き継ぎコード
- 8文字、表示は `XXXX-XXXX`。
- 使う文字：`ABCDEFGHJKMNPQRSTUVWXYZ23456789`（0/O、1/I/L など紛らわしいものを除いた31種）。約 8.5×10¹¹ 通り。
- 入力時は大文字にそろえ、ハイフン・空白は無視する。
- DBで一意。発行時に重複したら作り直す。
- 総当たり対策：入力の失敗回数を制限する（例：同じIPから10分に20回まで）。校内Wi-Fiは多くの人が同じIPになるので、厳しくしすぎない。アプリは1台構成なのでメモリ上のカウンタで十分。
- **IPの取り方**：本番はHTTPSを終端するプロキシの後ろで動くので、接続元のIPはそのままだと全員プロキシのIPに見える（全員まとめて制限されてしまう）。`X-Forwarded-For` ヘッダーから取る。
  - `X-Forwarded-For` は「元のIP, 途中のプロキシ…」と右に追記されていく。左側は利用者が自由に書けてしまうので、**自分たちのプロキシが追記した値（プロキシが1段なら一番右）**を使う。
  - プロキシが `X-Forwarded-For` を付ける設定になっているかを仮デプロイで確認する（9.1）。

### 5.3 チェックポイントとQR
- チェックポイントは**設定ファイル**で管理する（既存の `src/data/ExhibitionInfo.json` と同じ方式）。案：`src/data/checkpoints.json`
  ```json
  [
    {
      "id": "cp-01",
      "name": "チーム出the印",
      "exhibitionId": "ex-01",
      "floor": "2",
      "location": "T28",
      "hint": "2階 T28 の入口に掲示"
    }
  ]
  ```
- この設定ファイルは**公開してよい情報だけ**にする（名前・場所など）。リポジトリは GitHub で public なので、QRに入れるトークンは**ファイルに書かない**（下記）。
- QRの中身：`https://fes.sazanami.dev/s/<token>`（約35文字。QRは29×29マスに収まる。`/stamp/c/` にすると33×33マスになり、読み取りにくくなる）

#### トークン（リポジトリに置かない）
- トークンは、秘密鍵とチェックポイントIDから**計算で作る**：`token = HMAC-SHA256(CHECKPOINT_SECRET, id)` を、引き継ぎコードと同じ31種の文字（5.2）で表した**先頭8文字**。
  - 秘密鍵 `CHECKPOINT_SECRET` は環境変数で持つ。`.env*` は `.gitignore` 済みなので、リポジトリには載らない。
  - リポジトリにはIDしかなく、秘密鍵がなければトークンを作れない。トークンを保存するファイルやテーブルも要らない。
- サーバーで受け取ったとき：全チェックポイントについてトークンを計算し、一致するものを探す（数十件なので一瞬）。比較は時間が一定になる方法（`timingSafeEqual`）で行う。
- 掲示物を作るスクリプトも、同じ秘密鍵を環境変数から読んでトークンを計算する。
- 手入力用のコードには、このトークン8文字をそのまま使い、`XXXX-XXXX` の形でQRの下に印刷する。入力のルールは引き継ぎコードと同じ（大文字にそろえる・ハイフン無視）。
- 交換用QRの署名鍵（`RALLY_SECRET`、5.4）とは**別の鍵**にする。片方を作り直しても、もう片方に影響しない。
- 流出したとき（掲示物の写真共有など）：不正は許容なので基本は何もしない。どうしても止めたいときは `CHECKPOINT_SECRET` を変えて全部刷り直す（取得済みのスタンプはIDで記録しているので消えない）。
- 印刷物の作り方は 9.2 を参照。
- 交換条件が8個なので、**チェックポイントは8か所以上**必要。ちょうど8か所なら全部回る必要がある。
- 一覧画面の表示順・名前・場所もこの設定から出す。未獲得のスタンプには場所のヒントを出し、マップ（`/`）へリンクする。

### 5.4 景品と交換
- 景品は1種類なので、景品の設定ファイルは作らない。設定は次の3つだけ（例：`src/data/rally.json`）
  ```json
  {
    "requiredStamps": 8,
    "prizeName": "（景品名）",
    "exchangePlace": { "name": "（サークル名）", "floor": "", "location": "" }
  }
  ```
- **1人1回だけ交換できる**。
- 在庫切れ：在庫はシステムでは持たず、交換所で「品切れ」と伝える。必要になったら設定に `soldOut` を足して、画面に表示する。
- 交換用QRの中身：`参加者ID・有効期限（5分）` に、サーバーの秘密鍵で署名を付けたトークン。
  - 署名があるので、参加者側で中身を書き換えられない。
  - 有効期限があるので、古いスクショは使えない。
- 交換の確定は、DBの「交換記録」テーブルに参加者IDを一意で保存する。2回目は失敗し、スタッフ画面に「交換済み（〇時〇分）」と出る。

### 5.5 スタッフ認証
- PINは環境変数（`STAFF_PIN`）で1つだけ設定する。
- 正しければ署名付き Cookie（`sr_staff`、有効期限は当日中）を発行。
- PINの失敗回数も 5.2 と同じように制限する。
- スタッフ画面にも QR スキャナ（`/stamp/scan` と同じ部品）を使う。

### 5.6 開催時間
- スタンプの取得・交換は、**開催日の 10:00〜16:00（日本時間）** だけ受け付ける。
- 開催日と時間は環境変数で持つ（例：`RALLY_DATES=2026-xx-xx,2026-xx-xx`、`RALLY_OPEN=10:00`、`RALLY_CLOSE=16:00`）。サーバーの時計はUTCのことが多いので、日本時間に直して判定する。
- 時間外は「受付時間外です（10:00〜16:00）」と表示する。スタンプ一覧と引き継ぎは時間外でも使える。
- 16:00 直前に8個そろった人のため、交換所の締め切りを少し遅らせるか（例：16:15まで交換だけ受け付ける）は当日の運用で決める。設定で交換の締め切りだけ別に持てるようにしておく。
- 準備・テスト中は期間を広げて使う。

## 6. データベース

`src/db/schema.ts` に追加する。チェックポイントと景品は設定ファイルにあるので、DBには「誰が何を取ったか」だけを置く。

### participants（参加者）
| 列 | 型 | 説明 |
|---|---|---|
| id | uuid PK | 参加者ID（Cookie の値） |
| recovery_code | text UNIQUE NOT NULL | 引き継ぎコード（ハイフンなしで保存） |
| created_at | timestamptz NOT NULL | 参加日時 |
| last_seen_at | timestamptz NOT NULL | 最後に使った日時（集計用） |

### stamps（獲得スタンプ）
| 列 | 型 | 説明 |
|---|---|---|
| participant_id | uuid FK → participants.id | |
| checkpoint_id | text NOT NULL | 設定ファイルの `id` |
| acquired_at | timestamptz NOT NULL | 獲得日時 |
| | PK (participant_id, checkpoint_id) | **重複読み取りはここで防ぐ**（`ON CONFLICT DO NOTHING`） |

### redemptions（景品交換）
| 列 | 型 | 説明 |
|---|---|---|
| participant_id | uuid PK, FK → participants.id | PKなので**1人1回**になる |
| stamp_count | integer NOT NULL | 交換時点の獲得数（記録用） |
| redeemed_at | timestamptz NOT NULL | 交換日時 |

- 個人情報を含む列はない。
- 設定ファイルからチェックポイントを消しても、DBの記録は残る（表示時に存在するものだけ数える）。

## 7. サーバー処理（Server Actions / Route Handlers）

| 処理 | 入力 | 主な動き |
|---|---|---|
| 参加する（Server Action） | なし | ID と引き継ぎコードを発行 → DB保存 → Cookie 設定 |
| 引き継ぐ（Server Action） | 引き継ぎコード | 回数制限 → 検索 → Cookie を付け直す |
| スタンプを付ける（Server Action） | チェックポイントのトークン | パンフ内スキャナ・手入力から呼ぶ。期間チェック → トークンからチェックポイントを特定 → stamps に保存（重複は無視）→ 「新規／獲得済み」を返す |
| QRのリンク先（Route Handler `GET /s/[token]`） | URLのトークン | 4.3 の分岐。Cookie があればスタンプを保存して `/stamp?got=…` へ、なければ `/stamp/join?cp=…` へリダイレクト |
| 参加＋スタンプ（Server Action） | チェックポイントのトークン | `/stamp/join` の「はじめて参加する」。参加とスタンプ付与をまとめて行う |
| 引き継ぎ＋スタンプ（Server Action） | 引き継ぎコード、トークン | `/stamp/join` の「引き継ぎコードを入力する」。引き継ぎとスタンプ付与をまとめて行う |
| 自分の状態を取る | （Cookie） | 獲得済みチェックポイント・交換済みかどうか |
| 交換用QRを発行 | （Cookie） | 時間内か・8個あるか確認 → 署名トークンを返す |
| スタッフログイン | PIN | 回数制限 → 照合 → スタッフ Cookie |
| 交換内容を確認 | 交換トークン（スタッフのみ） | 署名・期限を検証 → 獲得数・交換済みかを返す |
| 交換を確定 | 交換トークン（スタッフのみ） | 条件を再確認 → redemptions に保存（すでにあれば失敗） |

- 獲得数や交換条件の判定は**必ずサーバー側**で行う。画面側の表示は信用しない。
- 秘密鍵（署名用）は環境変数 `RALLY_SECRET` で持つ。
- 中身の処理（スタンプ保存・参加など）は `server-only` のモジュールにまとめ、Server Action と Route Handler の両方から呼ぶ。Server Action 側は薄くする（`data-security.md` の Data Access Layer の考え方）。
- **Server Action はプロキシの設定に影響される**：Next.js は Server Action の呼び出し時に `Origin` ヘッダーと `Host`（または `X-Forwarded-Host`）を比べ、一致しないと処理を中止する。HTTPS を終端するプロキシが `Host` を書き換えていると、参加ボタンなどがすべて失敗する。
  - 対策：プロキシで元の `Host` を渡す（または `X-Forwarded-Host` を付ける）。それができない場合は `next.config.ts` の `serverActions.allowedOrigins` に `fes.sazanami.dev` を入れる。

## 8. 決定事項と未定事項

「期限」は、それまでに決めないと困る時点。

| 項目 | 期限 | 状態 | 内容 |
|---|---|---|---|
| 本番ドメイン | 印刷前 | 決定 | `fes.sazanami.dev` |
| QRのURLの形 | 印刷前 | 決定 | `https://fes.sazanami.dev/s/<token>`（5.3） |
| 本番のHTTPS | 印刷前 | 決定 | 仮デプロイで HTTPS で開けることを確認済み（10章） |
| チェックポイントの数・設置場所 | 印刷前 | **未定** | 8か所以上が必要（5.3） |
| 景品 | — | 決定 | 1種類。8個で交換 |
| 交換の回数 | — | 決定 | 1人1回 |
| 交換所 | — | 決定 | サークルの展示場所 |
| 受付時間 | — | 決定 | 10:00〜16:00 |
| スタンプの見た目（共通か、チェックポイントごとか・担当者） | 画面作成まで | **未定** | |
| Cookie利用の案内文・学校側の確認が要るか | 画面作成まで | **未定** | 参加画面に「端末にIDを保存します」程度の一文 |
| QR読み取りライブラリ | 実装開始時 | 決定 | 読み取りは `jsqr`（映像を canvas に描いて解析。iOS Safari でも動く）、生成は `qrcode`（交換用QR・掲示物） |
| 景品名・サークルの展示場所（階・教室） | 当日まで | **未定** | `rally.json` に入れる |
| 開催日 | 当日まで | **未定** | 環境変数に入れる |
| 交換所の運用（スタッフ画面の端末・PINの共有・人員） | 当日まで | **未定** | 5.5 |
| 交換所の締め切り（16:00ちょうどか、少し延ばすか） | 当日まで | **未定** | 5.6 |

### 進め方（実装の順番）
チェックポイントが未定でも、仮のデータで最後まで通して動かせる順にする。

1. DBのテーブル（6章）
2. 参加・引き継ぎ ── **作ったらすぐ仮デプロイ（`fes.sazanami.dev`）で「参加する」を押して、Server Action が通ることを確認する**（7章のプロキシの注意）。あわせて、回数制限用のIPが `X-Forwarded-For` から正しく取れているかもログで確認する
3. スタンプ獲得：まず `/s/[token]`、次にパンフ内スキャナ
4. スタンプ一覧（`/stamp`）
5. 景品交換・スタッフ画面
6. 掲示物を作るスクリプト（9.2）

## 9. 運用

### 9.1 準備
1. 企画側の決定をもとに `checkpoints.json` / `rally.json` を作る
2. 本番の環境変数（`STAFF_PIN`, `RALLY_SECRET`, `CHECKPOINT_SECRET`, `RALLY_DATES`, `RALLY_OPEN`, `RALLY_CLOSE`）を設定する。今の `compose.prod.yaml` の `app` は `DATABASE_URL` しか渡していないので、次の作業が要る（実装時に行う）
   - `compose.prod.yaml` の `app.environment` に上の変数を追加する（値は `.env.production` から `${STAFF_PIN}` のように渡す）
   - `.env.example` に変数名と説明を追加する（値は書かない）。今の `.gitignore` では `.env.example` も無視されているので、あわせて直す
   - 開発用の `compose.yaml` にも同じ変数を追加する
   - 秘密鍵は十分に長いランダムな値にする（例：`openssl rand -base64 32`）
3. 仮デプロイで、プロキシの設定を確認する
   - `Host`（または `X-Forwarded-Host`）が `fes.sazanami.dev` のまま届いていること（Server Action のため）
   - `X-Forwarded-For` が付いていること（回数制限のため）
4. 掲示物を作って印刷・掲示する（9.2）。トークンは `CHECKPOINT_SECRET` から作るので、本番の値を決めてから刷る
5. 掲示後に、全チェックポイントを実機で1回ずつ読んで確認

### 9.2 チェックポイント掲示物の印刷（案）

#### 1枚に載せるもの
```
┌───────────────────────┐
│  学園祭2026 スタンプラリー      │
│  CHECKPOINT  No.3              │
│  チーム出the印（2F T28）       │
│                                │
│        ┌─────────┐            │
│        │   QR    │  ← 6cm角以上 │
│        └─────────┘            │
│      コード：K3VQ-9XT2         │  ← カメラが使えない人の手入力用
│                                │
│  パンフレットの「スタンプ」→   │
│  「QRを読む」で読み取ってね    │
│  スマホのカメラで読んでもOK     │
│  8個集めると景品と交換できます │
└───────────────────────┘
```
- QRは1つだけにする。リンク先が `/s/<token>` なので、パンフをまだ開いていない人がスマホのカメラで読んでも、そのまま参加とスタンプ獲得ができる（4.3）。パンフへの案内用QRを別に置くと、どちらを読むか迷わせてしまう。
- サイズは **A5（A4の半分）** を基本にする。A4用紙1枚に2枚刷って切れば、紙とラミネートの数が半分で済む。

#### QRの作り方
- **URLは短くする**：URLが短いほどQRのマス目が粗くなり、遠くからでも、古いスマホでも読みやすい。そのためパスは `/s/<token>` に決定（5.3）。
- **誤り訂正レベルは M**。中央にロゴを重ねる場合だけ H にする（ロゴで隠れた部分を補うため）。
- **周りに余白**（マス4つ分以上）を空ける。枠や模様をQRのすぐ近くまで寄せない。
- **SVG（ベクター）で出力**する。拡大してもぼやけない。
- 黒と白で刷る。色付きにするなら、濃い色のQRを薄い背景に載せる。逆（白いQRを黒地に）は読めないスマホがある。

#### 作り方の選択肢
| 方法 | 内容 | 向いている場合 |
|---|---|---|
| **A. スクリプトでPDFまで作る（推奨）** | `scripts/` に `checkpoints.json` からQR（SVG）を作り、A5のHTMLテンプレートに流し込むスクリプトを置く。ブラウザで開いて「PDFに保存」→ 印刷 | チェックポイントの追加・変更があっても、作り直しが一瞬で済む。名前や番号の書き間違いが起きない |
| B. QR画像だけ作り、デザインツールで配置 | スクリプトはQRのSVGだけを出力し、Canva や Illustrator で装飾して書き出す | 掲示物の見た目にこだわる場合。デザイン担当がいる場合 |

チェックポイントがまだ決まっていない今のうちに、Aの仕組みとテンプレートを作っておけば、決まった時点ですぐ印刷できる。見た目を凝りたければ、Aのテンプレートの背景画像だけデザイン担当に作ってもらう方法もある。

**出力物の扱い（リポジトリが public のため）**
- スクリプトが作るQR・HTML・PDFにはトークンが入るので、**コミットしない**。出力先は `.gitignore` に入れたフォルダにする（例：`/print/`）。
- デザインツール（B）に渡すときも、共有範囲を担当者だけにする。
- スクリプトは `CHECKPOINT_SECRET` が設定されていないと止まるようにする（空の鍵で作った、本番と違うQRを刷ってしまわないため）。

#### 印刷・掲示
- **つや消しのラミネート**にする。つやありは照明が反射して、QRが読めない角度ができる。
- 高さは **床から120〜150cm**（目の高さより少し下）。窓際・逆光・直射日光の当たる場所は避ける。
- 入口の横など、読む人が立ち止まっても通行のじゃまにならない場所に貼る。
- 各チェックポイントにつき **予備を1〜2枚** 刷って、交換所に置いておく。
- 本番前に1枚試し刷りして、**1m離れた場所から**、iPhone・Android（古めの機種も）で読めるか確認する。

#### いたずら対策
- 上から別のQRシールを貼られる可能性はゼロではない。パンフ内スキャナは**`https://fes.sazanami.dev/s/` で始まるQRだけを受け付ける**ようにしておく（不正なサイトへ連れて行かれるのを防ぐ）。
- 見回りのついでに、掲示物が剥がれたり貼り替えられたりしていないか確認する。

### 9.3 当日
- QRが剥がれた・読めないとの連絡 → 予備を貼る。手入力用コードで代用もできる
- 引き継ぎコードをなくした参加者 → 復元はできない（個人と結びついていないため）。新しく参加してもらう。景品が軽いので許容

### 9.4 終了後
- 集計（参加者数・チェックポイントごとの獲得数・交換数）を取って記録する。数だけで、個々の記録は残さない
- 学園祭終了から一定期間（例：1か月）で participants / stamps / redemptions を削除する

## 10. 非機能

- **規模**：来場者数千人程度を想定。1件ずつの書き込みは小さく、今の PostgreSQL 1台で足りる
- **HTTPS 必須**：カメラ（`getUserMedia`）と `Secure` Cookie のため。`.dev` ドメインはブラウザがHTTPSでの接続を強制する（HSTSプリロード）ので、HTTPSなしでは開けない。仮デプロイで、`https://fes.sazanami.dev` でパンフを開けることを確認済み。開発時は localhost で動く
- **カメラ**：iOS Safari は `BarcodeDetector` に対応していないので、QR読み取りはライブラリを使う（実装時に選定）。カメラの許可を断られた場合は手入力に案内する
- **対応ブラウザ**：iOS Safari / Android Chrome / LINE・Instagram のアプリ内ブラウザ
- **プライバシー**：保存するのはランダムなIDと獲得記録だけ。外部の解析ツールに参加者IDを送らない

## 11. テスト観点

| 観点 | 確認すること |
|---|---|
| 参加 | 参加ボタンで ID と引き継ぎコードが出る。再読み込みしても参加済みのまま |
| スタンプ | パンフ内スキャナで取れる。同じQRをもう一度読むと「獲得済み」で、数は増えない |
| 標準カメラ | Cookie のないブラウザで開くと「はじめて参加／引き継ぎ」の選択に分かれ、どちらでもスタンプが付く |
| リダイレクト | `/s/[token]` を開くと、Cookie ありなら `/stamp?got=…`、なしなら `/stamp/join?cp=…` に移る。Cookie なしのときに参加者が増えていない |
| 本番環境 | 仮デプロイで Server Action（参加ボタン）が通る。回数制限が利用者ごとに効き、全員まとめて制限されない |
| 引き継ぎ | 別ブラウザで引き継ぎコードを入れると、同じスタンプが見える。小文字・ハイフンなしでも通る。何度も間違えると制限される |
| 無効なQR | 存在しないトークンで「無効なQR」になる。期間外は「受付時間外」になる |
| トークン | 掲示物スクリプトで作ったトークンとサーバーの判定が一致する。`CHECKPOINT_SECRET` を変えると古いトークンが無効になる。リポジトリ内にトークンや印刷物が含まれていない |
| 交換 | 7個以下では交換用QRが出ない。期限切れのQRはスタッフ画面で弾かれる。2回目の交換は「交換済み」で失敗する |
| 受付時間 | 9:59 と 16:00 以降は受け付けず、10:00 からは受け付ける（日本時間で判定できているか） |
| スタッフ | PINなしでは `/staff/exchange` を開けない |
| 実機 | iOS Safari / Android Chrome / LINEアプリ内ブラウザで、上の流れを通しで確認 |
